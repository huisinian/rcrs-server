问题 1：Collection<EntityID> unexploredBuildings 为什么用 Collection 而不是 List？
遵循面向接口编程规范，Collection 是 List、Set 各类集合共同的顶层父接口，做类型声明时使用顶层接口，可以解除上层代码和 ArrayList 这类具体实现类的绑定。后续如果业务需要把底层存储结构从 List 换成 HashSet 等别的集合，上层调用逻辑不用改动，代码扩展性更强。
业务场景仅需要集合通用能力：元素新增、遍历、判定包含关系，不需要 List 独有的按下标取值、下标插入这类方法，用 Collection 能缩小对外暴露的接口能力，避免开发者误用 List 专属 API，减少代码出错概率。
提升代码通用性，方法参数、成员变量声明使用 Collection，能够兼容所有 Collection 体系下的集合实现，接收参数的适配范围比限定 List 更广。
问题 2：EnumSet.of (...) 是什么作用？对比普通 Set 有什么好处？
EnumSet.of (...) 作用
EnumSet 是专门适配枚举类型的集合实现类，of 是一组静态工厂方法，用来快速批量填入枚举常量，直接构造完成初始化的 EnumSet 实例，省去循环逐个调用 add 方法填充元素的冗余代码。
相对普通 HashSet 这类通用 Set 的优势
运行性能更强：EnumSet 底层依靠紧凑的位向量存储枚举成员，新增、判存、删除操作开销很低；普通 HashSet 依托哈希表运作，要做哈希计算、解决哈希冲突，额外性能消耗更多。
内存占用更低：枚举常量数量固定，位向量只占用少量比特位存放成员状态；HashSet 需要维护哈希槽、链表节点，同等元素量下内存开销高出不少。
类型约束更严格：EnumSet 强制仅存放对应枚举的常量，编译阶段就可以拦截类型错误；通用 HashSet 在泛型约束失效时，有存入异类对象、触发运行时类型转换报错的隐患。
自带枚举声明顺序：集合遍历顺序严格贴合枚举类里常量编写的先后顺序；HashSet 不保障固定的元素排布顺序。
API 适配枚举场景：EnumSet 配套了范围截取补全枚举集合等专属方法，做枚举集合区间运算时，手写通用 Set 代码会繁琐很多。
